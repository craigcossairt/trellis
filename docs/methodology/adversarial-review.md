# Adversarial review: have a different model read it

A model reviewing its own work is the weakest review available, and it does not feel weak
from the inside. It re-reads its own reasoning and finds it persuasive, because the reasoning
is what produced the code in the first place. The blind spot that let the defect through is
the same blind spot that reads the defect as fine.

So for anything whose failure you would care about, **the reviewer should be a different model
family from the one that wrote it** - not a second pass by the same one, and not the same one
with a sterner prompt.

## What this actually buys, with a measurement

This template's own sync tool shipped with a skill file that said, in section 1:

> Do not offer to generate one from the current tree: a manifest built from an already-modified
> copy records your edits as if upstream had shipped them, and every future sync inherits that
> lie.

and then, about fifty lines later in section 4, instructed every copy to do exactly that. The
consequence was not cosmetic. Reproduced on a fixture: a file the adopter had edited and
*declined* moved from `localonly` to `apply` - reported as "SAFE TO TAKE" - on the very next
run, and their own application source appeared under "REMOVED UPSTREAM - decide whether to
keep".

That file was written, reviewed, mutation-tested and released. The model that wrote both halves
did not see the contradiction. A different model, reading it cold, opened with it.

The lesson is not "that model is better". It is that the contradiction was *visible* - plain
text, one file, fifty lines apart - and invisible **to the author**. That is the class of defect
this practice exists for, and there is no amount of care by the author that substitutes for it.

## Where to spend it

Reviews cost time and money, so spend them where the author's blind spot is most likely and the
failure is worst:

- **Anything that can destroy the user's work** - a tool that writes, deletes, overwrites or
  migrates. The author has been reasoning about the happy path for an hour.
- **Anything consuming an input space you are *inferring* rather than *enumerating*** - parsers,
  validators, anything reading markup, config or a third-party format. A full-red mutation
  battery does not cover this, and the next section says why.
- **Auth, permissions, and money.**
- **The instructions themselves** - a skill, a protocol, a prompt. Prose is not compiled and
  nothing checks it. The example above was prose.

## A red mutation battery is not a substitute

Mutation testing bounds the gap between **your code and your tests**. It cannot bound the gap
between **your code and reality**. A mutation perturbs code you already wrote, so it can only
expose something your tests fail to notice - never an input you never considered, and never a
rule you stated and then contradicted.

Both failures are routine, and they arrive looking like success: every mutation goes red, the
suite is green, and the defect is in the space neither the code nor the tests ever modelled. If
your only evidence is a red battery, you have evidence about your tests.

## How to run one so it is worth having

1. **Give the reviewer the artifact, not your summary of it.** A summary carries your framing,
   which is the thing you want tested. Point it at the files.
2. **Do not tell it what you think is risky.** You will get a careful examination of exactly the
   places you already looked.
3. **Keep reviewers blind to each other.** If you run two, do not show the second what the first
   said until it has committed its own take, then synthesise. An anchored reviewer is a rubber
   stamp - it agrees, you count it as confirmation, and you now have two votes from one opinion.
4. **Ask it to reproduce, not just to opine.** "Show me the input that makes this fail" separates
   a finding from a hunch.

## Then verify every finding before you act on it

A review from another model is **data, not a verdict**. It is generated by something with its
own blind spots, it is fluent, and fluent wrongness is the expensive kind. Check each finding
against the code yourself and grade it on the certainty ladder in `AGENTS.md` before changing
anything.

Expect a mix, and say which is which when you report back:

- Findings that hold exactly as described. Reproduce them, then fix them.
- Findings that are right about the defect and wrong about the mechanism. Fix the defect, and
  correct the mechanism out loud so the reasoning on record is the true one.
- Findings that are wrong. Say so plainly, with the evidence. A reviewer you never contradict is
  one you have stopped reading.

Reporting "the reviewer found five things" without having checked them is the same failure as
shipping unverified code, one level up.
